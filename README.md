# anomaly-net

**Русский** | [English](README.en.md)

Детектор аномалий в логах: автоэнкодер (PyTorch → ONNX), признаки — z-score относительно истории самого сервера. Две модели: **SSH** (`auth.log`, готова к использованию; автоэнкодер работает в паре с простым счётчиком неудач) и **веб-трафик** (`model_v1`, пока только на синтетике).

## Установка (SSH-детектор на Linux-сервер)

Требования: Linux, root, `python3` с модулем `venv`, лог `/var/log/auth.log` (Debian/Ubuntu; если логи идут только в journald, поставьте rsyslog).

```bash
git clone https://github.com/loar32/anomaly-net.git
cd anomaly-net
sudo ./install.sh                                 # без Telegram
# или с Telegram и языком сообщений (ru или en, по умолчанию ru):
sudo TG_TOKEN=<токен бота> TG_CHAT=<chat_id> ANOMALY_LANG=en ./install.sh
```

`install.sh` копирует файлы в `/opt/anomaly-net`, создаёт venv, ставит `numpy pandas onnxruntime`, добавляет в cron запуск раз в 15 минут и в конце делает пробный прогон по текущему логу. Повторный запуск безопасен: cron не дублируется, существующий `.env` с настройками Telegram сохраняется. Находки дописываются в `/var/log/anomaly-net.log`.

Детектор читает `auth.log.1` и `auth.log`, поэтому после еженедельной ротации знакомые IP не становятся «новыми». В режиме cron он разбирает только завершённые 5-минутные окна и помнит, о чём уже сообщил (`state.json` в каталоге установки): одно и то же окно или вход не приходит в Telegram дважды. Если Telegram недоступен, находки уйдут при следующем запуске.

Проверка вручную: `cd /opt/anomaly-net && .venv/bin/python detect.py /var/log/auth.log` — должна вывестись строка вида `окон N, аномальных M`.

**Важно:** `model_ssh.onnx` откалибрована на одном сервере с fail2ban (бан после 4 неудач за 10 минут) и фоном около 8 неудачных входов за 5 минут. На сервере с другим фоном переобучите модель на своих логах (нужно не меньше 4 суток нормы): положите `auth.log`, `auth.log.1` и, если есть, `auth.log.*.gz` в `logs/`, выполните `pip install -r requirements-train.txt`, затем `python ssh.py --from <начало нормы>` (например, `--from 2026-10-08T18:00`) и скопируйте новые `model_ssh.onnx` и `model_ssh.json` в каталог установки. Без `--from` нормой считается весь лог.

Тесты парсера: `python test_logs.py` (нужны только numpy и pandas).

## SSH-модель (`ssh.py`, `detect.py`)

Данные — `auth.log` одного сервера с 13.09 по 13.10.2026. До 8 октября сервер был под постоянным брутфорсом (около 32 неудачных входов за 5 минут). 8 октября в 17:36 включён fail2ban, и фон упал до 8. **Нормой считается период после fail2ban** (с 08.10 18:00), всё раньше — «прежний режим», который модель нормой не считает.

- Окна по 5 минут, 6 признаков: число неудач, уникальные IP, доля несуществующих пользователей, энтропия логинов, доля новых IP, доля самого активного IP.
- Нормализация: `z = (x − mean) / (std + 0.1)`, затем `sign(z)·log(1+|z|)`; mean и std — по обучающему периоду.
- Автоэнкодер 6→32→3→32→6 (ReLU).
- Период нормы делится по времени: обучение 08.10 18:00 – 11.10 14:15 (820 окон), подбор порога 11.10 14:20 – 12.10 13:00 (273 окна), проверка 12.10 13:05 – 13.10 11:50 (274 окна). Порог и проверка — на сутках, которых сеть не видела.
- Порог автоэнкодера — 99,5-й перцентиль ошибки восстановления на сутках порога. Счётчик — то же правило для числа неудач (больше 19 за 5 минут). **Окно аномально, если сработал автоэнкодер или счётчик.**
- Успешные входы в модель не входят: отдельное правило «вход с нового IP» сообщает о первом входе с адреса, которого не было в истории (`auth.log.1`, `auth.log`) и в `state.json`.

`python ssh.py --from 2026-10-08T18:00` обучает модель, печатает таблицу ниже и пишет `model_ssh.onnx` и `model_ssh.json` (порог, порог счётчика, mean/std, метрики). `python detect.py /var/log/auth.log` прогоняет лог через модель; `--recent 20` — режим cron (при первом запуске смотрит последние 20 минут, дальше — с места, где остановился).

### Результаты (доля помеченных окон)

| | автоэнкодер | счётчик неудач | вместе |
|---|---|---|---|
| ложные тревоги (сутки проверки) | 0.004 | 0.000 | 0.004 |
| прежний режим брутфорса (13.09–08.10) | 0.44 | 0.48 | 0.51 |
| перебор с одного IP (20 паролей к root) | 1.00 | 1.00 | 1.00 |
| ботнет (50 новых IP по 2 попытки, словарь логинов) | 0.00 | 1.00 | 1.00 |
| целевой подбор (обычный объём, но всё с одного нового IP по root) | 0.42 | 0.00 | 0.42 |
| медленный перебор (1 попытка с нового IP) | 0.025 | 0.005 | 0.030 |

Последние четыре строки — искусственные атаки: события вписываются в 200 случайных окон суток проверки, признаки пересчитываются с нуля.

- Автоэнкодер и счётчик дополняют друг друга. Ботнет для сети выглядит как «обычная картина, только крупнее»: в норме попытки и IP растут вместе, и сеть такое окно восстанавливает. Его ловит счётчик. Целевой подбор, наоборот, не меняет объёма, и счётчик его не видит; сеть ловит его по необычной структуре окна (один IP, один логин).
- Прежний режим помечен примерно наполовину: в часы затишья брутфорс по признакам не отличается от новой нормы.
- На всём периоде после fail2ban детектор помечает 0–5 окон в сутки, в основном счётчиком — это реальные всплески больше 19 неудач за 5 минут.

### Ограничения

- **Порог задаётся перцентилем**, поэтому около 0,5% окон нормы будут помечены по построению, даже если атак нет. На сутках проверки вышло 0,4%. Это уровень срабатываний, а не частота атак.
- **Размеченных реальных атак нет.** «Прежний режим» — другой режим трафика, а не разметка; атаки в таблице внедрены искусственно. Реальную полноту это не измеряет.
- **Один сервер и около 4,5 суток нормы.** Если в период нормы шла атака, модель выучила её как норму; проверки на это нет.
- **Фон после fail2ban — тоже попытки ботов** (1–3 попытки с адреса, ниже порога бана). Модель считает их нормой; убрать их можно только входом по ключу или сменой порта SSH.
- **Медленный перебор** (по одной попытке с разных IP) неотличим от фона.
- **Дрейф не отслеживается**: порог фиксированный. После смены настроек SSH/fail2ban или заметного изменения трафика модель нужно переобучить.
- Разбираются только строки sshd `Failed …` и `Accepted …` (метки времени ISO 8601 и классические syslog, свёрнутые rsyslog повторы); строки другого формата пропускаются.

## Веб-модель (`train.py`)

Обучена на синтетике: `pip install -r requirements-train.txt`, затем `python train.py` (пишет `model_v1.onnx` и `model_v1.json`). Учится только на норме, проверяется на серверах, которых не видела.

8 признаков: запросы, уникальные IP, доли ответов 4xx и 5xx, энтропия путей и user-agent, доля новых IP, неудачные SSH-входы. Признака «портов на IP» и сценария сканирования портов нет: в журнале веб-сервера портов нет, и в реальных логах такой признак всегда был бы константой. Автоэнкодер 8→64→4→64→8: при узком месте 8 сеть может просто копировать вход.

### Метрики (серверы вне обучения)

Порог — 99-й перцентиль ошибки на отложенной норме обучающих серверов, FPR и полнота — на серверах, которых модель не видела (поэтому FPR не равен 1% по построению).

| | автоэнкодер | isolation forest |
|---|---|---|
| FPR | 0.012 | 0.011 |
| brute_force | 1.00 | 1.00 |
| traffic_spike | 1.00 | 0.18 |
| path_scanning | 1.00 | 0.89 |
| credential_stuffing | 1.00 | 0.82 |
| slow_exfiltration | 0.89 | 0.08 |
| полнота (все) | 0.98 | 0.60 |

Проверено только на синтетических сценариях. В синтетической норме признаки связаны общим фактором нагрузки (запросы, IP, ошибки и энтропия растут вместе); без такой связи автоэнкодеру нечего сжимать. Реальные логи будут устроены иначе, это ещё предстоит проверить.
